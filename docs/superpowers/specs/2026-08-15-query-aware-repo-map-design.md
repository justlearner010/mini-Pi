# Query-aware TypeScript Repo Map design

## Status and relationship to Issue 9

This document is the Issue #9 design proposed for owner review. It supersedes
the Issue #9 section of `2026-08-14-large-project-intelligence-design.md` and
the fixed startup-map behavior in the existing compact-map implementation
plan. Issues #10 and #11 remain separate: this design finds candidate evidence;
it does not decide when exploration is sufficient or turn unobserved facts into
verified claims.

The implementation remains on the dedicated `codex/compact-project-map`
branch. After this specification is approved, the old implementation plan must
be replaced before production code changes continue.

## Goal

Given a TypeScript or JavaScript repository, mini-Pi builds a bounded local
repository index once, then derives a compact map for each user question. The
map should let the Agent identify plausible files and core symbols without
asking the model to enumerate or read the whole repository.

The desired exploration path is:

```text
question
  -> local index lookup
  -> compact candidate map
  -> read only candidate source ranges
  -> verify module relationships when necessary
  -> answer from inspected evidence
```

The Repo Map is navigation evidence, not an answer. Source bodies still have
to be inspected before the Agent states implementation details as facts.

## V1 non-goals

- No complete call graph or function-body semantic analysis.
- No embeddings, vector database, PageRank, or second LLM.
- No TypeChecker, inferred types, runtime module resolution, or installed-
  dependency analysis.
- No full multi-language symbol support. Non-TS/JS directories may appear only
  as unavailable scope.
- No dynamic-import, reflection, dependency-injection, or runtime-routing
  claims.
- No Repo Map dump in the TUI and no direct answer generated by the map.
- No broad source-code search tool, `find_references`, or symbol-body tool in
  this Issue.
- No permanent insertion of a complete map into conversation history.

## Chosen approach

V1 uses the TypeScript Compiler API in syntax-only mode. It parses supported
files locally without a Provider call and without evaluating the project. This
is deliberately different from asking the LLM to read every file: local CPU and
memory construct an index, while only a small question-specific rendering is
sent to the configured Provider.

The design has three cooperating parts:

1. **RepositoryIndex** — local structured data built once per CLI process.
2. **Transient Repo Map** — automatically rendered for the current question
   and included in every model request during that `Agent.run`, but not retained
   as full text after the run.
3. **`query_repo_map` Tool** — an optional SAFE refinement query over the same
   index when the automatic candidates are insufficient or conflicting.

The existing tools keep distinct roles:

| Tool | Role after Issue #9 |
| --- | --- |
| `scan_project` | broad fallback and non-TS/JS project shape |
| `query_repo_map` | locate TS/JS files and declarations relevant to a question |
| `read_file` | inspect exact source evidence, preferably by returned line range |
| `analyze_dependencies` | verify a bounded static dependency chain from an entry |

## Architecture and ownership

The five-file source structure remains intact.

- `tool.ts` owns source discovery, syntax parsing, the repository-index data
  model, deterministic ranking/rendering, and the bound `query_repo_map` Tool.
- `agent.ts` accepts per-run transient context and makes it available during
  every model request in that run without adding the full block to persistent
  conversation history.
- `cli.ts` builds one index after root selection, derives the automatic map for
  each prompt, and gives replacement Agents from `/login` or `/model` access to
  the same immutable index.
- `tui.ts` displays only safe summary state such as indexed file count and
  truncation; it never prints the map or source signatures.
- `llm.ts` remains Provider conversion only and receives the already-composed
  request messages.

```text
filesystem -> RepositoryIndexBuilder -> immutable RepositoryIndex
                                            |              |
user question -> query renderer ------------+              |
       |                                                    |
       +-> transient Agent context -> model -> query_repo_map
                                                |
                                                +-> same index
```

No repository index, cache, or source-derived map is written to disk in V1.

## Source discovery and resource bounds

Discovery includes `.ts`, `.tsx`, `.js`, and `.jsx`, including `.d.ts`. It
always excludes every dot-prefixed directory plus `node_modules`, `dist`,
`build`, and `coverage`. It respects root-level `.gitignore` patterns with
standard negation, rooted-pattern, directory-pattern, and last-match-wins
semantics. Nested `.gitignore`, `.git/info/exclude`, and global Git excludes are
reported as unsupported V1 scope rather than silently claimed as honored.

Paths are project-root-relative POSIX strings. Directory symlinks are not
followed. Files whose real path escapes the project root are rejected. Output
ordering is lexical and therefore deterministic across runs.

Hard limits are:

| Resource | V1 limit |
| --- | ---: |
| Supported source files parsed | 5,000 |
| Bytes parsed per source file | 512 KiB |
| Total supported source bytes parsed | 50 MiB |
| Candidates rendered per query | 8 |
| Automatic or Tool map text | 8,000 JavaScript characters |
| Dependency neighborhood | one incoming and outgoing hop |

Files are considered in lexical path order. A file beyond any bound is not
partially parsed. The index records counts and reasons for skipped files. Every
rendered map includes inspected counts plus explicit uninspected/truncated
scope. Index construction failure is recoverable: the session starts with the
existing tools and reports that indexed navigation is unavailable.

## Data model

The public TypeScript contracts are conceptually:

```ts
type SourceKind = "ts" | "tsx" | "js" | "jsx" | "dts";

interface SourceLocation {
  line: number;       // one-based
  column: number;     // one-based
}

interface ImportInfo {
  specifier: string;
  kind: "relative" | "alias" | "package" | "dynamic";
  resolvedPath?: string;
  exported: boolean; // true for export ... from
}

interface SymbolInfo {
  name: string;
  kind: "class" | "function" | "interface" | "type" | "enum" |
        "variable" | "method";
  signature: string;
  exported: boolean;
  location: SourceLocation;
  signatureTruncated: boolean;
}

interface FileInfo {
  path: string;
  sourceKind: SourceKind;
  imports: ImportInfo[];
  exports: string[];
  symbols: SymbolInfo[];
  parseDiagnostics: number;
}

interface RepositoryIndex {
  files: readonly FileInfo[];
  incoming: ReadonlyMap<string, readonly string[]>;
  outgoing: ReadonlyMap<string, readonly string[]>;
  entryCandidates: readonly string[];
  inspectedFileCount: number;
  inspectedBytes: number;
  skipped: Readonly<Record<string, number>>;
  truncated: boolean;
}
```

The concrete implementation may use serializable arrays instead of `Map`, but
must preserve these semantics and stable order.

## Syntax extraction rules

Parsing uses `typescript.createSourceFile`; V1 does not create a `Program` or
TypeChecker.

The index extracts:

- static `import` declarations, side-effect imports, `import type`, and
  `export ... from` declarations;
- relative imports resolved using the existing extension and `index` rules;
- alias-looking, package, and dynamic imports as marked unresolved facts, not
  resolved dependency edges;
- explicit named/default exports and export modifiers;
- top-level class, function, interface, type alias, enum, and simple identifier
  variable declarations;
- public methods of exported classes, including public constructors, while
  omitting private/protected methods and method bodies.

Signatures contain declaration syntax only. Function and method bodies and
variable initializer bodies are omitted. Whitespace is normalized; each
signature is capped at 240 characters and records whether it was truncated.
Anonymous/default declarations receive a stable display name such as
`default class` rather than a fabricated identifier. Syntax diagnostics do not
abort the whole index: the file retains facts recoverable from its AST and its
diagnostic count is reported.

## Candidate selection

Query ranking is deterministic and lexical, not semantic search. The renderer
normalizes case and splits paths/symbols/query terms across `/`, `.`, `_`, `-`,
and camelCase boundaries. V1 uses every nonempty normalized token; it has no
language-dependent stop-word list. Common words that match no indexed path or
symbol therefore contribute no score without risking removal of a real code
identifier.

Candidates are ordered by this tuple:

1. exact symbol/export identifier match;
2. number of symbol/export query-token matches;
3. number of basename/path query-token matches;
4. entry-candidate match;
5. number of incoming local dependencies;
6. lexical project-relative path.

Directly matched files are seeds. The renderer may then add one-hop incoming
and outgoing local dependencies, after matched seeds and within the same eight-
file cap. Every candidate names its selection reason. A zero lexical match does
not pretend relevance: it returns only bounded entry candidates and labels the
result `fallback candidates`.

## Rendered Repo Map contract

The automatic and Tool renderers use the same bounded textual format:

```text
REPO MAP
query: provider configuration
indexed: 42/42 supported files · 183 KiB

FILES
src/
├── cli.ts
└── llm.ts

DEPENDENCIES
src/cli.ts -> src/llm.ts

SYMBOLS
src/llm.ts
  interface LLMProviderConfig · line 18
  function createLLM(config: LLMProviderConfig): LLM · line 42
  reason: symbol/provider match; imported by src/cli.ts

SCOPE
source bodies not inspected
unsupported import resolution: aliases, packages, dynamic imports
index truncated: no
map truncated: no
```

Reduction priority is: `SCOPE`, candidate paths/reasons, matching symbols and
locations, dependency edges, nonmatching neighboring symbols, tree decoration.
The renderer drops complete low-priority lines or sections and never cuts a
path/signature in the middle. If any content is removed it emits
`map truncated: yes`.

The map must not contain source bodies, comments, initializer/default-value
expressions, API keys, environment variables, absolute project paths, full scan
results, or raw parse errors. An explicitly declared literal type may appear as
part of a public signature; arbitrary runtime string content may not. This is
metadata that the owner has authorized mini-Pi to send to the currently
selected Provider.

## Automatic transient context

Before each one-shot or interactive question, CLI renders a Repo Map using the
current user text. `Agent.run` receives it as transient context. The context is
placed after the stable system instructions and before conversational messages,
and is included in every Provider request made during that run.

The full automatic map is never appended to `Agent.history()`. On success,
failure, or max-turn termination it is discarded. The persistent history keeps
the normal user, assistant, and Tool messages. `/login` and `/model` retain the
conversation and immutable index, then future questions receive newly rendered
maps for the replacement model.

If index construction or rendering fails, `Agent.run` proceeds without the
transient block. Failure is represented as safe status, not raw filesystem or
parser output.

## `query_repo_map` Tool

The new Tool is bound to the session's immutable index and has this schema:

```json
{
  "type": "object",
  "properties": {
    "query": { "type": "string", "minLength": 1 },
    "limit": { "type": "integer", "minimum": 1, "maximum": 8 }
  },
  "required": ["query"],
  "additionalProperties": false
}
```

`limit` defaults to eight. The Tool is `SAFE`, because it reads only the
already-built local metadata index. It uses the same renderer and 8,000-
character cap as the automatic map. It cannot request source bodies, increase
dependency depth, rebuild the index, change the root, or bypass skipped scope.

The System Prompt teaches this decision rule:

- If the automatic map identifies a plausible candidate, use `read_file` on
  its declaration or nearby range.
- If candidates are absent, ambiguous, or conflict with newly inspected
  evidence, call `query_repo_map` once with a more precise code-oriented query.
- Do not call it merely to repeat the original query. Do not treat its output
  as proof of function-body behavior.

During the active run the Tool result is available normally. At run completion,
its full map is replaced in persistent history by a bounded breadcrumb of at
most 512 characters containing candidate paths and truncation state. This
prevents repeated refinement maps from accumulating across a long TUI session
while leaving a valid assistant-tool-result message pair.

## Error and degradation behavior

- Unsupported repository: show indexed navigation unavailable and retain
  `scan_project`/`read_file`; do not claim symbol support.
- Oversized or ignored file: skip it, increment the explicit reason count, and
  render it as uninspected scope.
- Parse diagnostic: keep recoverable declarations, record the count, and avoid
  quoting the raw diagnostic.
- Unresolved import: classify it; never invent a local edge.
- Empty query or invalid arguments: return a stable Tool error and no result.
- Renderer/index exception: fail closed for map claims but fail open for Agent
  usability; the existing tools remain available.
- Provider failure: follow existing safe Provider diagnostics; the map does
  not change error classification.

## Tests

### Functional tests

- Discover real `.ts/.tsx/.js/.jsx/.d.ts` files in deterministic order while
  honoring hard excludes and root `.gitignore`.
- Reject outside-root and symlink escape paths.
- Exercise exact 512 KiB, 5,000-file, and 50 MiB boundaries plus each
  truncation reason.
- Extract all supported imports, exports, declaration kinds, public exported-
  class methods, normalized signatures, and one-based locations.
- Prove comments, strings, function bodies, private/protected methods, and
  variable initializer bodies do not become symbols or dependencies.
- Prove alias/package/dynamic imports are marked but not resolved as local
  edges.
- Build exact incoming/outgoing dependency maps, including cycles.
- Render stable output at 4,000 and 8,000 characters without broken lines and
  with explicit scope/truncation.
- Validate the strict `query_repo_map` schema, cap, SAFE metadata, stable
  ranking, fallback candidates, and one-hop expansion.

### Agent and lifecycle tests

- Build the index exactly once per CLI process and reuse it through `/login`
  and `/model`.
- Generate a different automatic map for each user question.
- Include the same transient map in every Provider request in one Agent run,
  then prove the full map is absent from persistent history on success and
  failure.
- Make `query_repo_map` available only when an index exists; degraded sessions
  remain usable.
- Prove a refinement result is available during the run and becomes a
  <=512-character breadcrumb afterward.
- Prove already-clear candidates lead directly to `read_file`, while an
  ambiguous scripted run may refine once and cannot silently exceed bounds.
- Prove no map/source text is printed by TUI or written to credential/config
  storage.

### Behavioral navigation set

Against the mini-Pi repository revision recorded by the experiment:

1. Where is CLI handling implemented?
2. Which module defines the LLM provider?
3. Where is tool execution handled?
4. Which modules depend on Agent?
5. Where should I inspect provider configuration?

For every question, the expected file set is declared before running the
experiment. V1 acceptance requires the correct candidate in Top 3 for 5/5
questions and Top 1 for at least 4/5. The score uses paths only; a plausible
explanation cannot compensate for a wrong candidate.

## Experiment design and close gate

The report lives at `docs/experiments/9-query-aware-repo-map.md` and records the
exact repository commit, Node/TypeScript version, Provider/model when used,
question set, cache state, repetition count, and raw JSON artifact path.

Three variants are compared:

1. no Repo Map;
2. query-aware Repo Map capped at 4,000 characters;
3. query-aware Repo Map capped at 8,000 characters.

The deterministic local benchmark runs all questions and records index build
milliseconds, map render milliseconds, Top-1/Top-3 accuracy, model requests,
Tool calls by name, files read, returned Tool bytes, request characters, turns,
outcome, and truncation. Timing is reported but not used as a stable CI
threshold.

The candidate passes the deterministic close gate only when:

- functional and safety tests pass;
- 8,000-character Top-3 is 5/5 and Top-1 is at least 4/5;
- it does not increase failed outcomes or maximum-turn outcomes;
- median exploratory Tool calls before the first correct candidate read fall
  by at least 30% versus no-map;
- median source bytes returned before that read fall by at least 30%; and
- any failure, variance, or quality trade-off is written explicitly.

A live-Provider owner-run is a separate evidence tier, using the same Provider,
model, model parameters, question order, and three repetitions per variant.
It records Provider-reported input/output tokens when available, end-to-end
latency, Tool calls, candidate accuracy, and answer rubric. Monetary cost is
reported only from an explicitly recorded pricing snapshot; otherwise it is
`NOT MEASURED`. The PR may demonstrate deterministic improvement without a
live run, but it must not claim lower real token cost or latency until the live
evidence supports that claim.

The 4,000-character variant determines whether the extra 4,000-character
budget materially improves candidate accuracy. The default remains 8,000 only
if it improves Top-1/Top-3 or reduces exploration without regressing the answer
rubric; otherwise the report recommends 4,000.
